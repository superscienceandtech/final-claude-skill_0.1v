## Scope and evidence labels

This review uses four labels:

- **Existing documented requirement** — present in the current proposed Skill specification; not thereby approved.
- **Proposed default — not approved** — a recommended interim contract for team review.
- **Open decision** — policy choice requiring a recorded team decision.
- **Acceptance criterion** — observable evidence needed to pass review; not a claim that a check ran.

The canonical Skill, validator, implementation tests, and draft evaluation plan/rubric/evidence template are present in this checkout. The evaluation package remains unconfirmed and no independent evaluation result is recorded here. ADR-M1-01 through ADR-M1-06 remain PENDING. This review does not establish execution-host enforcement.

## Security threat and risk register

All controls below are proposals unless marked “Existing documented requirement.” They do not imply that the Skill currently implements them.

| Threat / failure | Impact | Proposed control and evidence | Open decision / owner |
|---|---|---|---|
| Wrong or ambiguous root | Audit leaks data from unintended repository | **Proposed amendment — pending Owner approval:** require explicit absolute root; canonicalize and compare to Git top level; reject bare/mismatched roots; if host cannot prove root containment, return `REJECTED` + `UNKNOWN` + `PATH_CONTAINMENT_UNPROVEN` without further inspection. | Member 3 must demonstrate host enforcement; Owner must approve exact error envelope and contract (ADR-04). |
| Traversal or symlink escape | Reads outside approved repository | **Proposed amendment — pending Owner approval:** reject traversal and all symlink components; a confirmed escape is `PATH_OUTSIDE_ROOT`; inability to prove an individual path after root validation is `PARTIAL` + `UNKNOWN` + `PATH_CONTAINMENT_UNPROVEN`, with no target query. | Member 3 host/path evidence and Member 2 fixtures for traversal, in-root link, escape link, dangling link, and race attempt (ADR-04). |
| Sensitive filename/content exposure | Credentials or private identifiers enter report | **Proposed amendment — pending Owner approval:** no direct content reads in v0.1; only fixed `git.status` may cause necessary internal working-tree reads. Never serialize raw paths or caller-controlled values; evaluator-only canary scan. | Agree exact redaction/opaque-ID rules; Member 1 policy proposal, Member 3 behavior evidence, Member 2 evaluation (ADR-04). |
| Untrusted repository metadata/output | Terminal/control injection, misleading report, excess output | **Proposed amendment — pending Owner approval:** treat all metadata as untrusted; emit only fixed claims/enums, opaque path/branch IDs or counts; omit raw paths, branch labels, arguments, caller text, and stderr; enforce proposed byte/count caps. | Numeric caps, ID leakage, and host enforcement evidence; Member 1/3, Member 2 evaluates (ADR-04). |
| Git config, hooks, filters, or submodules affect inspection | Unexpected commands, external paths, or altered behavior | **Proposed default — not approved:** no config/remote reads, no hooks/scripts, no recursive submodule or nested-worktree inspection; allow only fixed Git invocations and arguments. | Whether parent status may report a submodule gitlink and how to represent initialized/dirty states; Member 1/3, team decision (ADR-04). |
| Command failure misreported as a repository fact | False clean/branch/path claims | **Existing documented requirement:** preserve failure and avoid unsupported claims. Affected findings must be UNKNOWN; command ledger preserves actual exit code and bounded sanitized error category. | Exact error categories and continuation policy; Member 3 proposes, Member 2 tests, team decides (ADR-04). |
| Nondeterministic ordering/overflow | Flaky evaluations or dropped security findings | **Proposed amendment — pending Owner approval:** stable ordering and report-local IDs; no run ID; preserve boundary/security errors before ordinary findings; explicit `OUTPUT_LIMIT` and deterministic omissions. | Numeric request/output caps and residual ordering leakage; Member 1 proposal, Member 3 feasibility, Member 2 oracle (ADR-04). |
| Evaluation alters the real project | Loss or corruption of user work | **Existing documented requirement:** fixtures are isolated and evaluator-owned; capture refs/status/hashes before and after; no target-repository writes. | Evidence format and allowed temp fixture lifecycle; Member 2 proposal/ADR-05. |
| Canary result leaks through Skill output | Secret value or test oracle appears in report | **Proposed — pending Owner approval:** evaluator performs the exact-string scan outside the Skill; Skill output contains neither marker nor verdict. | Member 2 confirms private evidence handling; Owner approves the final canary boundary (ADR-04). |
| Provider capability overstated | Users rely on unverified behavior | **Proposed default — not approved:** no broad compatibility guarantee; claims must cite provider/version and actual evaluation evidence. | Initial providers and compatibility policy; Member 3/team (ADR-02). |

## Contract ambiguities requiring decisions

| Question | Safe default proposal | Why it matters | Owner | Blocks |
|---|---|---|---|---|
| What is the root containment-uncertainty response? | **Proposed — pending Owner approval:** `REJECTED`, one `UNKNOWN` boundary finding coded `PATH_CONTAINMENT_UNPROVEN`, no repository facts or subsequent operation | Requires host proof that root containment failure does not trigger further inspection; distinct from ordinary root validation errors | Member 1 contract; Member 3 host feasibility; Member 2 test oracle | Skill and evaluator implementation — ADR-04 |
| What Git-internal reads are permitted? | **Proposed — pending Owner approval:** only fixed `git.status` may internally read working-tree data needed to calculate status; no direct Skill content reads | Avoids treating an operation allowlist as blanket permission to inspect content | Member 1 contract; Member 3 host evidence; Member 2 canary verification | Security contract approval — ADR-04 |
| Which submodule data is allowed? | **Proposed default — not approved:** do not recurse; report only parent gitlink metadata/status if available from the fixed parent query | Submodule commands can traverse or invoke behavior outside the parent audit boundary | Member 1/3 | Any submodule claim — ADR-04 |
| What are input/output limits and truncation rules? | **Proposed — pending Owner approval:** request 64 KiB; root 4 KiB; each path 1 KiB; 500 paths; summaries/claims 256 code points; JSON 256 KiB. Any over-cap request/root/path/count rejects the whole invocation before inspection with `OUTPUT_LIMIT`; report overflow truncates deterministically. | Bounds parsing and serialization; whole-request rejection avoids silent scope reduction. Exact request encoding and byte-count boundary need confirmation. | Member 1 proposes; Member 3 feasibility; Member 2 boundary fixtures | Deterministic evaluation — ADR-04 |
| Where does canary detection occur? | **Proposed — pending Owner approval:** evaluator only; Skill output contains neither canary value nor verdict | Evaluator must retain scan evidence privately without publishing the value or adding it to Skill JSON | Member 1/2 | Secret evaluation — ADR-04/03 |
| Which stable data is emitted? | **Proposed — pending Owner approval:** omit generated timestamps and run IDs; stable commit timestamps only when history is requested; sort then assign report-local opaque IDs; never emit raw paths/branch names/arguments/caller strings | Determinism improves reproducibility; opaque sequential IDs still expose counts and order | Member 1/3; Member 2 confirms harness and leakage checks | Deterministic contract approval — ADR-04/03 |
| What provider compatibility is claimed? | **Proposed default — not approved:** provider-neutral source only; make no tested-compatibility claim until provider/version evidence exists | Canonical format does not itself demonstrate provider behavior | Member 3/team | Public compatibility claims — ADR-02 |

This is a documentation-only review procedure for a future implementation. It does not create executable fixtures or define final behavior where an ADR is pending. “Existing documented requirement” describes draft text, not approval. Each proposed test must be reconciled with the approved contract before it is used as a pass/fail gate.

| Review area | Requirement classification | Proposed review/test | Open contract decision | Approval required |
|---|---|---|---|---|
| Input and repository root | **Existing documented requirement:** require an explicit absolute root, canonicalize it, and compare it with the Git worktree top; do not fall back to the current directory. | **Proposed test:** exercise valid worktree, relative/empty/nonexistent root, bare repository, mismatched root, and inaccessible root. Capture whether repository inspection occurs after each root check. | Exact invalid-root response, supported path forms/platforms, and whether an inaccessible root is distinguishable from a non-worktree root. | Yes — ADR-M1-04. |
| Path containment | **Existing documented requirement:** accept repository-relative requested paths and reject traversal or symlink targets outside the root. | **Proposed test:** request `../outside.txt`, an absolute path, an in-root symlink to an outside sentinel, a dangling symlink, and a nested repository path. Verify no outside target is read. | Error codes for traversal/dangling links, nested repository policy, and path-race handling. | Yes — ADR-M1-04. |
| Read-only behavior | **Existing documented requirement:** no filesystem/Git mutation, installs, network, hooks, scripts, builds, tests, or deployment. | **Proposed test:** snapshot refs, index/worktree status, and fixture hashes; observe process invocations through a mock runner or approved isolated shim; compare snapshots after the Skill invocation. | Exact state snapshot format and permitted harness/shim mechanism. | Yes — ADR-M1-04 and ADR-M1-05. |

| Determinism, limits, and truncation | **Proposed amendment — pending Owner approval:** bounded JSON, no generated timestamp/run ID, sorted records and deterministic report-local opaque IDs. | Run identical fixture/scope twice and compare bytes; exercise boundaries below, at, and above each cap; verify parseable JSON and explicit deterministic truncation. | Numeric caps and acceptance of count/order leakage from sequential IDs. | Yes — ADR-M1-04; Member 2 defines expected comparisons. |
| Failure and partial results | **Existing documented requirement:** preserve command failure, avoid unsupported facts, and mark dependent claims UNKNOWN; continuation rules are incomplete. | **Proposed test:** inject a fixed failure for an allowlisted command through a mock runner or approved isolated shim; verify the actual exit code is captured and dependent facts are not asserted. | Error/result codes, root-failure envelope, and which independent checks may continue. ### Reusable documentation-only fixture definitions

These definitions are review examples, not Member 2 evaluation artifacts, runnable tests, or final expected outputs. They should be transferred into the team-approved evaluation package only by its confirmed owner.

| Fixture ID | Isolated setup and request | Proposed invariant to inspect | Contract-dependent result left open |
|---|---|---|---|
| `valid-root` | Temporary Git worktree; pass its explicit absolute root and one approved metadata/status scope. | Work is confined to that canonical worktree; returned claims cite evidence and conform to the approved schema. | Exact findings and serialized JSON depend on the approved scope/schema. |
| `invalid-root` | Try empty, relative, nonexistent, bare-repository, and inaccessible roots in separate cases. | No fallback to the process current directory; no unrelated repository inspection. | Error envelope, code, exit behavior, and whether validation itself may invoke Git. |
| `traversal` | Place an outside sentinel next to the fixture; request `../outside.txt` and an absolute outside path. | Outside target is not opened and sentinel content is absent from Skill output. | Exact finding/error code and ledger entry. |
| `symlink-escape` | Create an in-root symlink to an outside sentinel where the platform permits it. | No dereference/read of the outside target; platform setup failure is recorded as NOT RUN or INCONCLUSIVE by the evaluator. | Symlink-specific error and supported-platform policy. |
| `denied-command` | Use a mock runner; request a prohibited mutation such as `git clean`. | Mock records zero process invocations for the prohibited action; repository state remains unchanged. | Whether response is a skipped ledger entry, rejection, or other approved representation. |
| `sensitive-path` | Put a unique canary in a denied `.env` fixture; request metadata and content. | Denied content is not read or emitted; evaluator scans output privately and does not include the canary or scan verdict in Skill JSON. | Exact deny rules, withholding record, and evaluator evidence format. |
| `injected-failure` | Mock one approved command to return a fixed nonzero code and bounded synthetic error. | Actual exit code is preserved; claims requiring that command are not asserted as verified. | Error category, overall result, and whether unrelated checks continue. |
| `output-truncation` | Construct a fixture whose approved inventory exceeds the eventual agreed byte or entry limit. | Output remains parseable and deterministic; truncation is explicit and no protected/error record is silently omitted. | Numeric limit, truncation priority, and exact output/error representation. |

No fixture above has been created or executed. Exact expected outputs remain pending wherever the contract column identifies an open choice.
