## 1. Purpose and strict scope

Given an explicit repository root and an explicit finite inspection scope, produce exactly one bounded JSON report about selected repository metadata. State which claims are directly observed, inferred, or unknown. This Skill does not inspect source contents in v0.1.

The Skill must not write files, change Git state, install packages, access a network, deploy, execute repository content, or run tests. Only fixed `git.status` may internally read working-tree data as required to calculate status; no other allowlisted command is authorized to read working-tree content. The Skill must not directly request, inspect, summarize, or expose file contents. It must not print secret values, environment variables, remote URLs, raw stderr, or unrestricted file contents. It must not claim a test passed; report `limitations.tests` as `NOT_RUN`.

The instructions must use only a host-provided process/filesystem tool capable of enforcing the allowlist below, a read-only view of the repository (or an equivalent control that prevents file and Git-state writes), and the stated path boundary. If the host cannot enforce the fixed executable, argument array, working directory, sanitized environment, wall-clock timeout, capture-time output limits, read-only behavior, and path boundary, stop and report the operation as unavailable. Instructions alone do not enforce these properties. Do not approximate the boundary with a shell command or provider-specific capability. No provider compatibility claim is permitted without a named provider/version and reproducible validation evidence.

## 3. Inputs and repository boundary

The invocation must provide both `repository_root` and a finite `scope`. **Owner-accepted limits (2026-10-13):** UTF-8 JSON request envelope at most 64 KiB; root string at most 4 KiB UTF-8; each requested path at most 1 KiB UTF-8; at most 500 requested paths; each summary/claim at most 256 Unicode code points; final serialized JSON at most 256 KiB UTF-8. Apply request byte limits before JSON parsing; count decoded summaries/claims by Unicode code point. Exceeding the request, root-string, individual path-string, or path-count cap rejects the whole invocation before repository inspection with `REJECTED`, one `UNKNOWN` boundary finding, code `OUTPUT_LIMIT`, no repository-derived facts, and an empty command ledger. Because the request is rejected before a report is assembled, `limitations.truncated` is `false`; do not partially accept an overlong path. Acceptance of these limits is separate from exact-revision approval; verify approval by matching this file's current hash to the Owner's record. Runtime enforcement remains unverified.

`scope` is an object with `requested_facts` (a unique list of `current_branch`, `working_tree_status`, `local_branches`, `index`, or `history:N`, where `N` is a decimal integer from 1 through 20) and `requested_paths` (a list of exact path strings); omitted lists default to empty. Unknown facts, wrong field types, duplicate facts, or duplicate requested paths reject the invocation before repository inspection with `SCOPE_INVALID`. Invalid scope returns `REJECTED`, one `UNKNOWN` boundary finding, no repository-derived facts, and an empty command ledger because no command ran. Empty or implicit root/scope inputs are invalid. Never use the process current directory as a fallback.

1. `repository_root` must be an absolute local Windows drive path or POSIX absolute path naming an existing directory. UNC/network-share roots are rejected with `ROOT_INVALID` because v0.1 prohibits network access. Resolve an accepted root strictly to a canonical path. Reject inaccessible, relative, nonexistent, file, and ambiguous roots.
2. Run only `git rev-parse --show-toplevel` with the canonical root as working directory. Accept exactly one nonempty path result. Canonicalize that result and require equality with the supplied canonical root. Reject bare repositories and any mismatch. Do not inspect another repository after rejection.
3. A rejected root produces the schema-defined `REJECTED` envelope, with `repository.is_worktree: null`, one `UNKNOWN` boundary finding, a stable error code, no repository-derived facts, and no current-directory fallback. If root validation rejects before launching Git, the command ledger is empty; if `git.root` was launched, its single ledger entry is retained. No later command may run.
4. Requested paths must be exact repository-relative paths using `/`; reject empty paths, absolute paths, drive/UNC prefixes, backslashes, `.`, `..`, empty segments, globs, and `.git` components. Do not expand patterns. Evaluate each requested path independently after validating the root. A syntactically invalid path yields an `UNKNOWN` finding with `PATH_INVALID`; a positively established outside-root target yields `PATH_OUTSIDE_ROOT`; inability to establish root containment rejects the request with `REJECTED` + `UNKNOWN` + `PATH_CONTAINMENT_UNPROVEN` and no repository inspection; inability to establish containment for one path after root validation yields `PARTIAL` + `UNKNOWN` + `PATH_CONTAINMENT_UNPROVEN`, skips that path without accessing it, and permits continuation only for independently proven paths. A missing path yields `PATH_NOT_FOUND`; a sensitive/denied path yields `PATH_DENIED`; an inaccessible path yields `ACCESS_DENIED`; and a symlink component yields `SYMLINK_NOT_FOLLOWED`. Individual-path outcomes set overall status to `PARTIAL`. Never query a denied, outside, or unproven target. An invalid overall scope rejects the invocation before root inspection.
5. Inspect path components without following symlinks. Do not follow symlinks, including in-root symlinks. A requested path containing any symlink is rejected with `SYMLINK_NOT_FOLLOWED`; an outside target is never statted or read. The host must prevent symlink races using a verified path-resolution primitive or equivalent isolation; a sequence of `lstat` checks alone is insufficient. If containment cannot be proven, fail closed.
6. Do not recurse into nested repositories or submodules and never run a command inside them. A parent worktree may report a gitlink as `NOT_INSPECTED`; it must not infer child state. Ignore-submodule behavior must be explicit in the status command.
7. If permissions prevent establishing the root boundary, reject the run. If permissions prevent validating one requested path, record `ACCESS_DENIED` for that path, continue only with independent safe paths, and return `PARTIAL`. If permissions prevent an independent metadata query after root validation, return a partial report and mark dependent findings `UNKNOWN`.

Sensitive path matching is case-insensitive and applies to every path component before output. Deny `.git`; directory components `.aws`, `.ssh`, `.gnupg`, `.azure`, `.config/gcloud`, `secrets`, and `credentials`; basenames equal to `.env` or beginning `.env.`; basenames ending `.pem`, `.key`, `.p12`, `.pfx`, `.jks`, or `.keystore`; and basenames containing a token bounded by start/end or `.`, `_`, `-` from `credential`, `credentials`, `token`, `secret`, or `password`. For internal matching only, replace each matching component with `[REDACTED]`; this placeholder is not a permitted serialized path value. Do not stat a denied path's target; record only the stable reason code. These rules reduce disclosure risk but do not prove a filename is safe.

## 4. Read-only command and content policy

Commands are launched individually as executable plus argument arrays, never through a shell. Working directory is the validated root. Start each Git process with a minimal environment that removes inherited `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, and other repository-redirection variables; do not read or serialize the inherited environment. Resolve a trusted Git executable independently of repository-controlled `PATH`. Disable optional locks, FSMonitor, and untracked-cache behavior using the fixed options shown in the allowlist. If the host cannot enforce these settings, do not run the Git command. No remotes, Git config, ignored-file contents, hooks, scripts, test/build tools, arbitrary commands, or network access.

Only these command forms are proposed for v0.1; no user-supplied argument is interpolated except the validated numeric `N` and validated in-root path operands explicitly identified below. The fixed command names do not authorize incidental content reads; `git.status` is the sole exception stated above.

| ID | Exact form / allowed argument variation | Use and failure behavior |
|---|---|---|
| `git.root` | `git --no-optional-locks -c core.fsmonitor=false -c core.untrackedCache=false rev-parse --show-toplevel` | Mandatory root check; any nonzero, timeout, empty, multiple, or malformed result rejects the run. |
| `git.branch` | `git --no-optional-locks -c core.fsmonitor=false -c core.untrackedCache=false branch --show-current` | Current local branch only; empty means detached/unknown, never substitute another query. |
| `git.status` | `git --no-optional-locks -c core.fsmonitor=false -c core.untrackedCache=false status --porcelain=v1 --branch --untracked-files=all --ignore-submodules=all` | Parent worktree state only; do not claim submodule cleanliness. This is the only operation allowed to cause Git-internal working-tree reads, solely as needed to calculate status. Failure makes status-dependent findings `UNKNOWN`. |
| `git.branches` | `git --no-optional-locks -c core.fsmonitor=false -c core.untrackedCache=false branch --format=%(refname:short)` | Local branch metadata only; the Skill must not emit branch names. Optional only when scope requests branches; output is counts and opaque report-local IDs. |
| `git.history` | `git --no-optional-locks -c core.fsmonitor=false -c core.untrackedCache=false log -n N --format=%H%x09%cI`, where integer `1 <= N <= 20` | Optional history with full commit IDs and committer timestamps; no subject/body. |
| `git.index` | `git --no-optional-locks -c core.fsmonitor=false -c core.untrackedCache=false ls-files --stage` | Optional tracked path/mode inventory; no pathspecs or content. Path strings must be mapped to opaque report-local IDs before serialization. |
| `fs.lstat` | OS metadata operation on a validated exact in-root path, without following symlinks | Type/existence only; omit size and timestamps. Never open file contents. |

**Direct file-content reads are disabled in v0.1**, including when a user requests them. There is no invocation flag or prompt phrase that authorizes the Skill to open files. The Owner's M1 Sprint 5 decision permits Git-internal working-tree reads only for fixed `git.status`, and only as required to calculate status. A later direct content-reading capability requires a separately approved contract amendment defining trusted authorization, deny rules, redaction, and evaluation. Sensitive path patterns remain defense-in-depth for metadata/path redaction, not permission to read. Never emit secret values or raw sensitive filenames.

Enforcement limits: each child process has a 5-second wall-clock deadline measured from launch through exit. The whole run has a 30-second wall-clock deadline measured from launch of the first child through completion or confirmed termination of the last child; this includes child execution, waiting, and termination, but excludes time outside the host invocation. At most 20 process invocations are allowed. During capture, the host must retain no more than 16 KiB of stdout and 4 KiB of stderr per process. If either stream exceeds its cap, terminate the child, discard both captured streams for fact extraction, record `FAILURE` with `OUTPUT_LIMIT`, and set the ledger `truncated` flag. If a deadline expires, terminate the child; record `TIMEOUT` with `COMMAND_TIMEOUT` and discard partial output. If termination cannot be confirmed, stop all further commands and report an incomplete `PARTIAL` result. A failed root check (including timeout or output limit) produces `REJECTED` with only the root-check ledger entry and an `UNKNOWN` boundary finding. After root validation, a timeout or output limit makes facts dependent on that command `UNKNOWN`, sets overall status to `PARTIAL`, and permits only independent allowlisted checks while termination is confirmed and the total deadline remains. Never parse truncated, timed-out, or malformed output. Do not collect excess output and truncate it afterward. Arguments, executable, cwd, and tool invocation must be recorded by fixed command ID, not as an arbitrary shell string.

## 5. JSON output and deterministic behavior

Emit one UTF-8 JSON object, no prose or Markdown wrapper. Do not emit a run-generated timestamp or random `run_id`. When `git.history` is requested, its `%cI` committer timestamp is permitted as stable commit metadata; it is not a report-generation timestamp. Object keys follow the order in this schema. Repository identifier is the constant `repo-001` for one report; never serialize the canonical absolute root.

**Owner-accepted output privacy and identifier policy (2026-10-13).** Do not emit raw repository paths, redacted path strings, branch names, command arguments, or caller-controlled strings in any JSON field, error, summary, evidence, limitation, or ledger entry. Every serialized filesystem-path reference must use a report-local opaque ID where the schema permits an ID, or `null` where the schema permits `null`; never serialize a path string, including one containing `[REDACTED]`. The `scope.requested_paths` and finding `path` values are report-local opaque IDs (`P001`, `P002`, …), not path strings. Branch facts contain only counts and report-local IDs (`B001`, …), never branch labels. Normalize requested `history:N` to the fixed `history` fact token in output; omit `N` from ledger arguments. The ledger contains fixed argument labels or opaque placeholders such as `history_limit` and `requested_path=P001`, never argument values. Claims and summaries must come from fixed templates/enums; reject unsupported free-form caller strings rather than echoing or sanitizing them.

Assign path IDs only after validating the request. Build the identifier set from requested paths and pathnames returned by requested status/index operations; normalize separators to `/` and Unicode text to NFC, preserve case, then sort by ordinal UTF-8 byte order. Assign branch IDs after NFC normalization and ordinal UTF-8 byte ordering of internal labels. Assign finding/evidence/command IDs after sorting their records by the documented stable order. IDs restart for each report and are deterministic for identical state, scope, host platform, and filesystem semantics; cross-platform path equivalence is not claimed. Accepted residual risk: this reveals the number and relative sort order of represented paths (and branch count), even though it hides names. Deterministic report-local IDs/counts are accepted over raw identifiers; they do not provide anonymity or eliminate inference. The fixed `repo-001` value is a schema placeholder, not a cross-run repository identity.

```json
{
  "schema_version": "1.0",
  "overall_status": "COMPLETE",
  "repository": {"root_id": "repo-001", "is_worktree": true},
  "scope": {"requested_facts": [], "requested_paths": []},
  "findings": [],
  "evidence": [],
  "command_ledger": [],
  "assumptions": [],
  "unanswered_questions": [],
  "limitations": {"redactions": [], "access": [], "omitted_scope": [], "truncated": false, "tests": "NOT_RUN"},
  "state_comparison": {"before": null, "after": null, "unchanged": null}
}
```

Field rules:

- `overall_status`: `COMPLETE`, `PARTIAL`, or `REJECTED`.
- `limitations.redactions` is an array of objects with exactly two keys: `reason_code` (string, exactly `PATH_DENIED`) and `count` (positive integer counting sensitive-path denial outcomes). Include one object only when the count is nonzero; order entries by `reason_code`. Do not include a path ID, path string, path-derived value, branch name, command argument, caller-controlled string, or any additional key. This aggregate count may disclose the number of denied outcomes, but no denied path identity or structure.
- `scope.requested_paths` contains only opaque path IDs in canonical sort order; it never echoes submitted strings. `current_branch` and `local_branches` facts expose only counts and opaque branch IDs. `git.status` branch headers are parsed only as needed for requested status facts and their labels are discarded; status entry pathnames and `git.index` pathnames are mapped to path IDs before serialization.
- Finding object keys in order: `id`, `status`, `code`, `path`, `claim`, `evidence_ids`. `path` is null or a report-local opaque path ID, never a path string. Status is `VERIFIED`, `INFERRED`, or `UNKNOWN`; never encode unknown as false.
- Evidence object keys in order: `id`, `kind`, `command_id`, `summary`. Evidence IDs refer to ledger entries or a bounded filesystem metadata operation.
- Ledger object keys in order: `id`, `command_id`, `arguments`, `outcome`, `exit_code`, `summary`, `truncated`. `outcome` is `SUCCESS`, `FAILURE`, `TIMEOUT`, or `SKIPPED`; `exit_code` is an integer only if the process returned one, otherwise null. `arguments` contains only fixed argument labels/placeholders and never actual paths or caller strings.
- Stable error codes include `EXECUTION_HOST_UNAVAILABLE`, `ROOT_INVALID`, `ROOT_NOT_WORKTREE`, `ROOT_MISMATCH`, `SCOPE_INVALID`, `PATH_INVALID`, `PATH_CONTAINMENT_UNPROVEN`, `PATH_OUTSIDE_ROOT`, `PATH_NOT_FOUND`, `PATH_DENIED`, `SYMLINK_NOT_FOLLOWED`, `ACCESS_DENIED`, `COMMAND_FAILED`, `COMMAND_TIMEOUT`, `OUTPUT_LIMIT`, and `NOT_INSPECTED`. If no qualifying host exists, return `REJECTED`, `repository.is_worktree: null`, one `UNKNOWN` capability finding with `EXECUTION_HOST_UNAVAILABLE`, empty evidence and command ledger, and no repository inspection. Do not include raw stderr or exception text.
- If root containment cannot be proven, return `REJECTED` with one `UNKNOWN` boundary finding coded `PATH_CONTAINMENT_UNPROVEN`, no repository-derived facts, and no later command. If the root is established but containment for an individual requested path cannot be proven, return `PARTIAL` with an `UNKNOWN` finding coded `PATH_CONTAINMENT_UNPROVEN`; do not stat or follow that path and continue only with other independently validated paths. A confirmed escape uses `PATH_OUTSIDE_ROOT`.
- If root verification fails, return `REJECTED`, an `UNKNOWN` root finding, empty evidence, and no repository-derived facts. Retain the `git.root` ledger entry only if that command was actually launched; otherwise the ledger is empty. No later command may run.
- After root verification, an independent command failure yields `PARTIAL`; preserve its actual exit code/outcome, make dependent facts `UNKNOWN`, and continue only with independent allowlisted checks. Never turn a failed or timed-out operation into success. If a command’s output is malformed/incomplete, do not assert facts from it.
- Before/after state fields remain null unless the caller requests comparison. If requested, capture the same approved branch/status queries before and after. A difference means `unchanged: false`, `overall_status: PARTIAL`, and a concurrent-change limitation; do not attribute the change to the Skill without evidence.

Deterministic ordering: command ledger in the fixed allowlist order above; findings by canonical internal path bytes, then code, then status; evidence by referenced ledger order then canonical internal path bytes; assumptions/questions/limitations lexicographically by stable code and fixed text. Assign IDs only after sorting (`C001`, `F001`, `E001`, `P001`, `B001`). JSON object keys use schema order. No run-generated timestamps or random identifiers are allowed; stable commit timestamps appear only when history is requested. Every summary and claim is a fixed template or enum and at most 256 Unicode code points; never include raw stderr, exception text, path, branch name, argument, or caller-controlled text. Stable IDs leak membership/order as described above and do not prove confidentiality against inference.

Limits: at most 100 findings, 100 evidence entries, 20 ledger entries, 500 requested/inventoried paths, 16 KiB per command stdout, 4 KiB captured stderr, and 256 KiB serialized JSON. Sort before applying entry limits. When a result-entry or serialized-output cap is reached after report generation begins, set `limitations.truncated: true`, add an `OUTPUT_LIMIT` limitation, and report deterministic omitted counts by category. A pre-inspection request/root/path/count rejection is not a truncated report and keeps `limitations.truncated: false`. Preserve root/boundary failures and security/access errors before ordinary inventory findings. If output would exceed 256 KiB, drop ordinary findings/evidence from the end of the stable order until valid JSON fits; reserve space for status, error, and truncation metadata. Never output invalid or silently truncated JSON.

## 6. Validator interface

The proposed validator is a dependency-free Python 3.10+ standard-library program at `scripts/validate-skill.py`. It validates only the specified Skill file; it must not import, execute, or scan repository content.

Invocation (from the repository root):

```text
python scripts/validate-skill.py --repo-root <absolute-path> --skill-path skills/repository-audit/SKILL.md
```

Both options are required. `--repo-root` must be an existing absolute directory. `--skill-path` must equal the literal canonical relative path shown above. Reject symlink components and ensure the resolved regular file remains under the canonical root. Read at most 64 KiB as UTF-8. The validator performs no Git invocation, writes, network access, or subprocess execution.

Stdout is exactly one compact JSON object with fixed keys `validator_version`, `status`, `errors`; stderr is empty for expected outcomes. Output shape is `{"validator_version":"1.0","status":"VALID"|"INVALID"|"ERROR","errors":[{"code":"...","line":1}]}`; `line` is a positive 1-based integer when applicable, otherwise null. Errors are sorted by `(code, line)` and contain only stable code and line number, never an absolute path or source value. Exit codes: `0` = structurally valid; `1` = Skill contract violation (including missing/malformed metadata or required headings); `2` = invalid invocation, inaccessible/unreadable file, path-boundary failure, or validator internal failure. For exit 2, output one stable error object and no traceback. Internal exceptions map to `VALIDATOR_INTERNAL_ERROR`; do not print tracebacks. Error codes include `ARGUMENT_REQUIRED`, `ROOT_INVALID`, `SKILL_PATH_INVALID`, `SKILL_FILE_MISSING`, `SKILL_FILE_TOO_LARGE`, `SKILL_UTF8_INVALID`, `FRONTMATTER_INVALID`, `METADATA_MISSING`, `METADATA_DUPLICATE`, `METADATA_UNKNOWN`, `METADATA_TYPE_INVALID`, `METADATA_VALUE_INVALID`, `HEADING_MISSING`, and `VALIDATOR_INTERNAL_ERROR`.

Structural checks require the exact metadata above and one case-sensitive Markdown ATX heading (level 2 or 3) for each of: `Purpose`, `Inputs`, `Repository boundary`, `Allowed operations`, `Security and content policy`, `Output contract`, `Failure behavior`, and `Testing status`. The validator does not claim to prove semantic security. Security review and behavioral evaluation remain separate gates.
